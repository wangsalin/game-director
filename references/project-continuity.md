# 跨会话续接与变更

## 恢复顺序

1. 核实工作区及适用 AGENTS.md；执行任务时检查 Git 状态和已有差异，保留用户改动。
2. 读项目 README 的路径索引，再读 `IMPLEMENTATION_STATUS.md`、`DECISIONS.md`、当前里程碑和最近验证记录。LITE 合并文件时按 README 的章节索引读取同等内容。
3. 只读当前任务相关的 Brief、规则、UI/资产或技术文档；完整编码交接首次审计时阅读全部适用规格，后续按变更增量读取。
4. 用工程、构建和日志核对旧状态，不仅凭“已完成”文字。缺少文件不代表可以从头生成覆盖已有项目。
5. 简述当前阶段、已确认方向、下一步和实际阻塞。信息足够就继续；用户说“继续”不是重新访谈的理由。

只读请求不落盘更新；执行请求在当前产物内更新记录，不建立第二套互相冲突的进度文件。

## 状态最小信息

使用[进度模板](../templates/IMPLEMENTATION_STATUS_TEMPLATE.md)和[决策模板](../templates/DECISIONS_TEMPLATE.md)。至少保留：

- 当前阶段、当前里程碑、最后更新时间、下一项可执行动作。
- 项目规模、目标平台、核心循环和不做清单的权威文件位置。
- 已完成产物及证据；未验证项、阻塞原因、最小解锁条件。
- 决策 ID、结论、状态、来源/理由、受影响的规则/文件；替代旧决策时保留链路。
- 假设的验证方式与最迟决定阶段，不能悄悄当成 confirmed。

任务状态 `not_started / in_progress / blocked / done` 与验证证据分开记录。证据分别为 implemented、compiled、editor-tested、simulator-tested、device-tested、released；未执行记录 `not_run`，不把这些证据当成必然连续的状态链。

## 需求变化

用户新的明确指令优先，不能用已锁定文档拒绝改动。先评估对范围、规则、数值、存档、资产和测试的影响；在授权范围内更新权威文件、决策、受影响的里程碑及测试。超出授权或会破坏数据的部分集中澄清，继续不受影响的工作。

不在两个文件各维护一套权威公式或状态枚举。引用规则 ID；改变规则时同步实现与回归用例，并在进度中指出哪些旧验证已失效。已有工程不为套本 Skill 的目录而搬迁。
